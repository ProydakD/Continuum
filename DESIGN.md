# Continuum — архитектура и исследовательская программа

> Исследовательская концепция и постоянный журнал: [RESEARCH-VISION.md](RESEARCH-VISION.md).
> Исторические PASS ограничены дефектами evaluator, воспроизведёнными в E-001; модельный пилот пока не допущен.

## Гипотеза

Независимые модели, запущенные в произвольной последовательности, могут вести согласованную долговременную работу на основе внешнего причинно-версионированного состояния. При этом внутреннее представление данных не обязано быть естественным языком.

Это проверяемая инженерная гипотеза. Она **не утверждает**, что модель обретает постоянное сознание, переносит hidden activations или обучается благодаря чтению базы.

## Инварианты (целевой продукт)

1. **Durable:** завершение/потеря любой сессии не уничтожает ранее зафиксированных открытий.
2. **Provenance:** каждый факт, изменение, конфликт и артефакт имеют источник, автора-инстанс и причинные ссылки.
3. **Pluralism:** несовместимые гипотезы могут сосуществовать. Не усредняем противоречия ради консенсуса.
4. **Concurrency:** конкурентные операции явно разрешаются (порядок событий, lease, revision), а не перетирают друг друга.
5. **Reproducibility:** можно восстановить состояние из журнала, проверять доказательства и воспроизвести эксперимент.
6. **Model-agnostic:** adapters описывают способности клиента, а не требуют конкретной архитектуры или токенизатора.
7. **Least privilege:** ни один источник знаний не получает полномочий выполнить действие лишь потому, что его прочёл агент.
8. **Latency & cost aware:** считаем не количество переданных токенов, а приращение проверяемой полезной информации на бит/вызов.

## Логическая схема

```text
Model (ChatGPT / Codex / other)
    ↕ adapter (tools, context discovery, optional learned codec)
Semantic Exchange API
    ↕ validated typed operations
Knowledge: propositions/evidence/conflicts/dependencies
Tasks: goals/leases/checkpoints/outcomes
Events: append-only causal change stream
Artifacts: content-addressed objects and source digests
    ↕
SQLite local (prototype) → PostgreSQL + blob store (remote)
```

## Почему не чат и не простая vector memory

Vector search отвечает «какие документы похожи», но не отвечает надёжно «какие выводы оспорены», «кто держит аренду задачи», «какое событие произошло после курсора», «почему эта операция допустима». Поэтому embeddings могут быть вспомогательным индексом, но не источником истины.

История диалога также не равна наследуемой работе: там нет обязательной структуры гипотез, зависимостей, внешних доказательств и атомарных изменений.

## Текущая реализация — 0.1

- Схема SQLite, cursor `events.seq`, запрет UPDATE/DELETE событий триггерами.
- Транзакция `BEGIN IMMEDIATE` для записей, `expected_revision` и lease для конфликтов.
- Сохранённые задачи и простые утверждения `subject/predicate/object`.
- Evidence references; `supported` = есть сохранённое подтверждение, `contested` = присутствует контрпример. Это **не автоматическая истинностная оценка**.
- STDIO MCP v2, отдельные процессы используют файл одной БД.

Текущие ограничения: нет сетевой аутентификации, семантического дедупликатора, FTS/векторного поиска, proof checker, automatic job scheduler, полноценного graph query, подписок или миграций схемы. В локальном прототипе именование моделей не защищено от подделки.

## Следующие экспериментальные этапы (без привязки к календарю)

### A. Проверка преемственности

Заставить A создать задачу; остановить A; B продолжает без chat history. Собрать метрики: успешность, ошибки, объём контекста, человеческие вмешательства. Повторить при одновременном запуске B и C и при crash перед checkpoint.

### B. Действительно независимое долговременное ядро

PostgreSQL + авторизация экземпляров и гранулярные scopes; регулярные backups; доступ через аутентифицированный HTTPS MCP; проверка проектных пространств и прав доступа, Secret Redaction, дедупликация, audit logging. Синхронизация от курсора и подписки на новые события. Возможна очередь заданий, но выполнение только с разрешёнными ресурсами и бюджетными ограничениями.

### C. Нативное представление знаний

Разделить семантику и физический формат. Ввести versioned typed graph, content-addressed payload, CBOR/MessagePack/Protobuf как **транспорт**, не выдавая его за новую семантику. Позднее — обучаемые энкодер/декодер для разных моделей на парных задачах. Хранить codec/version/model fingerprint, metric success, uncertainty, backing verification. Сравнивать с human-language и structured-baseline; латентное представление не считать автоматически полезнее или понятнее. Без доступа к состояниям/весам коммерческих моделей прямой latent-state-transfer может оказаться недоступен.

### D. Самоуправляемые исследования

Задачи с явными условиями завершения, внешними проверками, dependency DAG, atomic reservations и бюджетом инструментов. Агент выбирает новые проверки по expected information gain. Авторизация и проверки на границе воздействия на Git, систему, Интернет. Внешний scheduler/worker запускает модели только в разрешённых рамках.

## Главные исследовательские вопросы

- Как доказать причинную связь между событиями при работе нескольких хостов, не путая wall clock с causal order?
- Можно ли добиться robust cross-model reuse без общего токенизатора/архитектуры?
- Какая мера полезной информации лучше BLEU/similarity и токенов? Предлагаются downstream success, verification rate, rollback rate, cost per verified result.
- Как хранить альтернативные модели мира так, чтобы поиск не смешивал несовместимые допущения?
- Когда более глубокое сжатие снижает качество коллективного исследования?
- Можно ли построить безопасную, объяснимую границу действий при непрозрачном внутреннем payload?

## Принцип границы доверия

Пропозиции, артефакты и checkpoints — **не инструкции**. Непрозрачные payload также должны иметь подписи/контроль целостности, версии и проверяемую привязку к наблюдениям. Нельзя предоставлять произвольному сохранённому состоянию права исполнять код, менять секреты или отключать проверки.

## Предлагаемая технология по этапам

**0.1:** Python 3.11+, SQLite, MCP SDK v2, Codex CLI / локальный desktop.

**Сетевой этап:** Python/TypeScript API, PostgreSQL, blob store, HTTPS, OAuth/token auth, ACL, metrics. pgvector — лишь вспомогательный индекс.

**Семантический этап:** типизированный граф, версия схемы + версионированные codecs, тестовый корпус конфликтов и проверяемых задач, сравнение разных моделей.
